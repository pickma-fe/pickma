# UI/UX 및 접근성 Baseline 기준

T46~T49, T64, T65가 공통으로 참조하는 기준 문서다. 각 task는 이 문서를 선행 참조 기준으로 사용하고, 화면·컴포넌트 점검 시 아래 기준에 따라 진행한다.

---

## 1. 컴포넌트별 접근성 기준

### Button

- 버튼 텍스트는 동작을 명확히 설명하는 레이블을 사용한다. "확인", "닫기"처럼 맥락 없는 텍스트는 지양하고 "주문 취소", "매장 승인"처럼 대상을 포함한다.
- 아이콘만 표시하는 버튼은 `aria-label`을 반드시 제공한다.
- `disabled` 상태의 버튼은 `disabled` 속성을 사용한다. 비활성 이유를 스크린 리더에 전달하기 위해 포커스를 유지해야 할 경우에는 `disabled` 대신 `aria-disabled="true"`를 사용한다.
- `focus-visible:ring-2 focus-visible:ring-offset-2` 스타일을 적용해 키보드 포커스를 시각적으로 표시한다.
- 최소 터치 타깃 크기는 44×44px을 확보한다(3절 참고).

### Link (`<a>`, `next/link`)

- 링크 텍스트는 목적지나 동작을 독립적으로 설명해야 한다. "여기 클릭" 같은 표현은 금지한다.
- 새 탭에서 열리는 링크는 `target="_blank" rel="noopener noreferrer"` 및 `aria-label`에 "(새 탭에서 열림)" 설명을 포함한다.
- 링크에도 `focus-visible:ring-2` 스타일을 적용한다.

### Input / Form

- 모든 form control에는 연결된 `<label>` 또는 `aria-label`이 있어야 한다.
- placeholder는 label 대체가 아닌 보조 힌트로만 사용한다.
- 필수 필드는 `required` 속성 또는 `aria-required="true"`를 지정하고, 시각적으로도 표시한다.
- 인라인 오류 메시지는 해당 input과 `aria-describedby`로 연결한다.
- Headless UI `Field`/`Label` 컴포넌트를 사용하면 label–input 연결이 자동으로 처리된다.

### Table / List

- 데이터 테이블은 `<thead>`와 `<th scope="col">`로 헤더를 명시한다.
- 정렬 가능한 컬럼 헤더는 `aria-sort="ascending|descending|none"`을 지정한다.
- 목록에서 선택된 항목은 `aria-selected="true"` 또는 `aria-current`를 사용한다.
- 빈 상태(0건)는 단순 공백이 아닌 안내 메시지와 다음 행동 CTA를 포함한다(2절 참고).

### Modal / Dialog

- Headless UI `Dialog` 컴포넌트를 사용해 포커스 트랩과 `aria-modal="true"`를 보장한다.
- Modal 제목은 `DialogTitle`로 연결하거나 `aria-labelledby`로 명시한다.
- 닫기 버튼에는 `aria-label="닫기"`를 지정한다.
- Escape 키로 닫히지 않는 Modal은 닫기 방법을 명확히 안내한다.
- Modal 열림 시 배경 스크롤을 잠그고, 닫힘 후 포커스를 트리거 요소로 복원한다.

### Toast / Alert

- 사용자 행동 결과 알림은 중요도에 따라 `role="status"` 또는 `role="alert"`를 사용한다.
- 단순 정보는 `role="status"` (`aria-live="polite"`), 오류·경고는 `role="alert"`를 사용한다.
- 자동 사라지는 Toast는 충분한 지속 시간(최소 4초)을 확보하고, 스크린 리더가 읽기 전에 사라지지 않게 한다.

### Badge / 상태 표시

- 상태 정보를 전달하는 Badge는 `role="status"` 또는 `aria-label`로 상태 의미를 보조 기술에 전달한다.
- 색만으로 상태를 구분하지 않고 텍스트 또는 아이콘을 함께 사용한다.

### Image (`next/image`, `<img>`)

- 의미 있는 이미지(상품 이미지, 매장 대표 이미지)는 내용을 설명하는 `alt`를 제공한다. 예: `alt="피자 3종 세트"`, `alt="핸드메이드 베이커리 대표 이미지"`
- 장식용 이미지(배경, 구분선)는 `alt=""`로 설정해 스크린 리더가 건너뛰게 한다.
- 이미지 로딩 실패 시 alt 텍스트가 대체 정보로 표시되므로 누락하지 않는다.

## 2. UI 상태 처리 기준

화면의 모든 비동기 영역은 loading / error / empty / disabled 상태를 명시적으로 처리한다.

### Loading

- 데이터 fetch 중에는 스켈레톤 UI 또는 spinner를 노출하고, 빈 화면을 그대로 두지 않는다.
- 버튼 액션 중에는 버튼을 `disabled` 처리하고 시각적 피드백(로딩 표시)을 제공한다.
- 페이지 전환 로딩은 Next.js `loading.tsx`를 활용한다.

### Error

- API 오류 시에는 구체적인 안내 메시지와 재시도 방법을 함께 노출한다.
- 예: "주문 목록을 불러오지 못했습니다. 다시 시도해 주세요." + [다시 시도] 버튼
- 오류 메시지에 서버 내부 정보(stack trace, raw error code)는 포함하지 않는다.
- 예외 경계(`error.tsx`)는 복구 액션을 포함한다.

### Empty

- 데이터가 없을 때는 "목록이 없습니다"만 표시하지 않고, 다음 행동(CTA)을 함께 제공한다.
- 예: "등록된 상품이 없습니다. 첫 상품을 등록해 보세요." + [상품 등록] 버튼
- 빈 상태 메시지는 사용자 유형(Consumer/Seller/Admin)에 맞게 작성한다.

### Disabled

- 사용 불가 상태의 UI 요소는 `disabled` 속성을 사용한다. 비활성 이유를 안내해야 해서 포커스를 유지할 필요가 있으면 `aria-disabled="true"`를 대신 사용한다.
- 가능하면 왜 비활성화됐는지 이유를 간결히 안내한다.
- 예: "결제 완료 후 취소 가능합니다", "승인 대기 중인 매장은 수정할 수 없습니다"
- 미구현 기능의 disabled 처리는 8절을 따른다.

## 3. 반응형 UI 기준

Tailwind v4 breakpoint를 기준으로 한다: `sm`(640px), `md`(768px), `lg`(1024px), `xl`(1280px), `2xl`(1536px).

### 레이아웃

- Mobile-first 접근: 기본 스타일을 모바일 기준으로 작성하고, `md:`/`lg:` 이상에서 데스크톱 레이아웃을 적용한다.
- 주요 콘텐츠(상품 목록, 주문 요약, 매장 설정)는 `sm` 이하에서 1열, `md` 이상에서 그리드/분할 레이아웃을 사용한다.
- Sidebar/네비게이션은 모바일에서 하단 탭 또는 드로어로 전환하거나 Disclosure로 접는다.

### 터치 타깃

- 버튼, 링크, form control의 실제 터치 영역은 최소 44×44px을 확보한다.
- 작은 아이콘 버튼은 `padding`으로 클릭 영역을 늘리고, 시각적 크기와 터치 영역을 분리해도 된다.

### 하단 CTA 가림

- 모바일에서 고정 하단 네비게이션이 중요 CTA를 가리지 않도록 `pb-safe`와 네비게이션 높이를 합산한 `padding-bottom`을 적용한다.
- 주문 완료, 결제 진행 같은 핵심 CTA는 스크롤 없이 항상 접근 가능해야 한다.

### 테이블 모바일 표현

- 컬럼이 많은 테이블은 `sm` 이하에서 가로 스크롤(`overflow-x-auto`) 또는 카드형 레이아웃으로 전환한다.
- 테이블 가로 스크롤 시 첫 번째 열(식별자)은 고정하는 것을 검토한다.

## 4. 화면 완성도·시각 기준

### 색 대비

WCAG AA 기준을 따르되, 아래 예외를 인정한다.

| 텍스트 유형                                | 최소 대비                               |
| ------------------------------------------ | --------------------------------------- |
| 일반 텍스트(18px 미만 또는 14px bold 미만) | 4.5:1                                   |
| 대형 텍스트(18px 이상 또는 14px bold 이상) | 3:1                                     |
| 브랜드 컬러 primary 버튼 텍스트            | 3:1 권장 (달성 어려운 경우 최대한 근접) |
| disabled 상태 텍스트·컨트롤                | 적용 제외                               |
| 장식적 요소(divider, 배경 패턴)            | 적용 제외                               |
| 로고타입                                   | 적용 제외                               |

- 브랜드 컬러(밝은 계열) primary 버튼은 4.5:1 달성이 구조적으로 어렵다. 이 경우 가장 대비가 높은 글자색을 선택하고, 버튼 외곽선(border)이 주변 배경과 3:1 이상의 대비를 갖도록 보완한다.
- 색만으로 정보를 전달하지 않고 아이콘·텍스트를 보조로 사용한다.

### Focus Ring

- 키보드 탐색 시 모든 인터랙티브 요소에 `focus-visible:ring-2 focus-visible:ring-offset-2` 스타일을 적용한다.
- `:focus` 대신 `:focus-visible`을 사용해 마우스 클릭 시 ring이 표시되지 않도록 한다.
- ring 색상은 배경과 충분한 대비를 가져야 한다.

### 텍스트 Overflow

- 단일 라인 텍스트가 잘릴 가능성이 있는 곳에는 `truncate` 또는 `line-clamp-N`을 적용한다.
- 긴 텍스트를 `truncate` 처리할 때는 `title` 속성 또는 Tooltip으로 전체 내용 접근을 제공한다.
- 상품명, 매장명, 사용자 이름은 주요 화면에서 잘리지 않도록 충분한 너비를 확보한다.

### 간격·정렬

- 인접한 요소 간 간격은 일관된 Tailwind spacing 단위를 사용한다(4의 배수 기준: `gap-2`, `gap-4`, `gap-6`).
- 폼 레이블과 입력 필드 간 간격, 버튼 그룹 간격, 카드 내부 간격은 화면 내에서 통일한다.
- 우선순위 높은 CTA는 시각적으로 두드러지게(primary 스타일) 표현하고, 보조 액션은 secondary/ghost 스타일을 사용한다.

## 5. UX 자연스러움 기준

### 정보·CTA 우선순위

- 화면당 주요 CTA는 1개를 원칙으로 한다. 복수 CTA가 필요하면 primary/secondary를 시각적으로 구분한다.
- 파괴적 액션(삭제, 취소, 반려)은 확인 Dialog를 통해 2단계로 처리한다.
- 중요 정보(금액, 마감 시간, 재고)는 계층 상단에 노출한다.

### 오류 복구

- 폼 제출 오류는 제출 차단 없이 인라인 오류 메시지로 표시하고, 수정 후 재시도가 쉬워야 한다.
- 네트워크 오류는 자동 재시도 또는 명시적 [다시 시도] 버튼을 제공한다.
- 세션 만료는 사용자 입력을 보존한 채 로그인 리디렉션하거나 명확히 안내한다.

### 빈 상태 다음 행동

- 빈 상태는 사용자가 멈추는 곳이 아닌 시작하는 곳으로 설계한다.
- 관련 CTA가 없으면 탐색 경로(홈으로, 목록으로)를 제공한다.

### 반복 업무 흐름

- Seller/Admin처럼 반복 작업이 많은 흐름에서는 목록→상세→편집→저장 전환을 최소화한다.
- 저장/수정 완료 후에는 목록으로 자동 이동하거나 성공 피드백을 즉시 제공한다.

## 6. 기존 UI 보완 기준 (T64 범위)

아래 항목은 현황 조사에서 확인된 `src/components/common/**` 접근성 미비 사항이다. 실제 수정은 **T64** 범위에서 처리한다. T46~T49 점검 시 중복 수정하지 않는다.

| 컴포넌트   | 현황                                      | T64 개선 목표                               |
| ---------- | ----------------------------------------- | ------------------------------------------- |
| Button     | `aria-label` prop 없음 (아이콘 전용 버튼) | `aria-label` prop 추가                      |
| Pagination | `focus-visible:ring-2` 미적용             | focus ring 스타일 추가                      |
| Footer     | 링크 focus 스타일 없음                    | `focus-visible:ring-2` 적용                 |
| Badge      | aria 속성 없음                            | `role="status"` 또는 `aria-label` 기준 적용 |
| Modal      | `aria-modal` 명시 없음                    | Headless UI Dialog `aria-modal` 동작 확인   |

## 7. Keyboard Navigation 기준

### Tab 순서

- 화면의 Tab 순서는 DOM 순서와 일치하고, 시각적 레이아웃과 논리적으로 일치해야 한다.
- `tabindex` 조작은 최소화하고, 필요 시 `tabindex="0"`만 사용한다. `tabindex="1"` 이상은 금지한다.
- Modal 열림 시 포커스는 Modal 내부로 이동하고, 닫힘 후 트리거 버튼으로 복원한다.

### 키 동작

| 키                  | 동작 기준                                                  |
| ------------------- | ---------------------------------------------------------- |
| `Enter` / `Space`   | 버튼·링크 활성화. `role="button"` 요소에도 동일하게 적용   |
| `Escape`            | Modal/Dialog/Dropdown/Sidebar 닫기                         |
| `Arrow` 키          | Radio group, Tab panel, 드롭다운 옵션, 날짜 선택기 내 이동 |
| `Tab` / `Shift+Tab` | 인터랙티브 요소 순방향/역방향 이동                         |

### Skip Navigation

- 반복 네비게이션이 있는 페이지에는 본문 바로가기 링크("본문 바로가기")를 화면 최상단에 제공한다. 시각적으로는 포커스 시에만 표시해도 된다.

## 8. 501 미구현 UI 연결 처리 기준

501 미구현 endpoint 현황과 운영 노출 정책은 **`docs/api_spec.md` 13절**을 단일 source of truth로 사용한다. 이 문서에 중복 정의하지 않는다.

요약 원칙:

- real mode에서 501을 반환하는 endpoint에 연결된 버튼·링크는 활성 상태로 운영 화면에 노출하지 않는다.
- 해당 기능은 숨김 또는 `disabled` 처리하고, 필요하면 "준비 중" 또는 명확한 disabled reason을 제공한다.
- T46~T49 점검 시 `docs/api_spec.md` 13절을 확인하고, 목록에 있는 endpoint에 연결된 UI가 활성 노출되어 있으면 수정한다.
- 501 목록은 담당 task(T28, T31 등)가 완료되면 줄어드므로, 구현 task 완료 시 13절을 갱신한다.

## 9. 검증 방식 결정표

T46~T49·T64·T65는 아래 기준에 따라 검증 방법을 선택한다.

| 검증 방법      | 적용 범위                                                                               | 비고                                                    |
| -------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| **Storybook**  | 개별 컴포넌트 단위 — loading/error/empty/disabled 상태, aria 속성, focus ring 시각 확인 | 페이지 전체 렌더링은 Storybook으로 검증하지 않음        |
| **Playwright** | 페이지 단위 흐름 — form 제출, modal open/close, keyboard navigation 시나리오            | 자동화 테스트 대상 시나리오는 task 완료 기준에 명시     |
| **수동 검증**  | T46~T49·T64·T65 **모든 task에 필수** — desktop/mobile viewport 직접 확인                | 레이아웃, CTA 우선순위, 텍스트 overflow, 상태 표시 확인 |

### 수동 검증 체크리스트

다음 항목을 desktop(1280px 이상), tablet(768px~1024px), mobile(375px~430px) viewport에서 각각 확인한다.

- [ ] 주요 CTA가 가려지지 않고 접근 가능한가?
- [ ] 텍스트가 잘리거나 겹치지 않는가?
- [ ] loading/error/empty 상태가 각각 표시되는가?
- [ ] 비활성 버튼·기능에 이유가 안내되는가?
- [ ] 아이콘 전용 버튼에 레이블이 있는가?
- [ ] 키보드만으로 주요 흐름을 완료할 수 있는가?
- [ ] focus ring이 모든 인터랙티브 요소에 표시되는가?
- [ ] 501 미구현 기능이 활성 상태로 노출되지 않는가?

## 10. 컴포넌트 위치 규칙

### 현재 구조 문제

- Consumer 컴포넌트: `src/components/consumer/` (중앙화됨)
- Seller/Admin 컴포넌트: 일부 `src/app/` 페이지 근처에 위치 (분산됨)

### 목표 구조

모든 도메인 컴포넌트는 `src/components/{domain}/` 아래에 위치한다.

```
src/components/
  common/      # 도메인 무관 공통 컴포넌트 (Button, Input, Modal 등)
  consumer/    # Consumer 전용 컴포넌트
  seller/      # Seller 전용 컴포넌트
  admin/       # Admin 전용 컴포넌트
  auth/        # 인증 관련 컴포넌트
  payment/     # 결제 관련 컴포넌트
```

### 이동 방침

- 현재 `src/app/` 내부에 위치한 Seller/Admin 컴포넌트의 `src/components/{domain}/` 이동은 **T65** 범위에서 처리한다.
- T46~T49 작업 시 컴포넌트를 새로 추가할 경우, 이 규칙에 따른 위치에 생성한다.
- 기존 컴포넌트 이동은 T65 완료 전까지 현재 위치를 유지하고 T46~T49 범위에서 임의로 이동하지 않는다.
